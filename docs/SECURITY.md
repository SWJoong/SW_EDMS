# 🔐 보안·무결성 분석 및 보완 내역 (SECURITY.md)

> 이 문서는 SW_EDMS(사회복지기관 전자결재 샘플)에 대해 접수된 9가지 지적과,
> 추가로 발견한 지점들을 **무엇이 문제였고 / 무엇을 고쳤으며 / 무엇은 원리적으로 못 고치는지**로
> 정리한 것입니다. 코드 조각을 자랑하는 문서가 아니라, **"이 앱을 감사·지도점검에 올려도 되는가?"**
> 라는 질문에 정직하게 답하는 문서입니다.

---

## 0. 한 줄 요약

**이 저장소는 훌륭한 "학습 교재"이지만, 지금 이대로는 "법정 보존·감사 대상 기록(근태·회계)을 담는 운영 시스템"으로 쓰면 안 됩니다.**
전자결재는 하필 기록 무결성 요구가 가장 높은 영역이라, 자체 제작 난이도가 최상위입니다.
그래서 이 문서와 README 상단의 [무결성 등급표](../README.md#-무결성-요구-수준별-바이브코딩-관리-가이드)는
"바이브코딩으로 어디까지 가고, 어디서부터 검증된 도구에 맡길지"의 선을 긋는 데 초점을 둡니다.

핵심 통찰(지적해주신 분의 말 그대로):
> **외부 전자결재 업체가 지도점검을 통과하는 이유는 기술이 뛰어나서가 아니라,
> "기록을 만드는 주체"와 "기록을 보관하는 주체"가 분리되어 있기 때문이다.**

기술(해시체인·트리거·RLS)은 이 분리를 **흉내** 내는 도구일 뿐, 분리 자체를 대신하지 못합니다.

## 1. 지금 앱의 실제 구조 (오해 방지)

- 현재 배포 코드는 **브라우저 `localStorage` 기반 목업**입니다. 서버·DB·로그인·권한이 **없습니다.**
- `docs/supabase_schema.sql` 은 "나중에 붙일 예정"인 **의도된 운영 스키마**입니다.
- 따라서 지적사항은 두 층에 걸쳐 있습니다.
  - **운영 스키마 층** → `docs/supabase_schema.sql` 을 **무결성 강화본으로 전면 재작성**해 반영.
  - **데모 코드 층** → `src/services/storage.ts` 에 **원리를 시연 + 한계를 주석으로 정직하게 명시**.

> ⚠️ `localStorage` 에서는 서버 시각 고정, 위·변조 방지, 삭제 흔적 보존, 사용자 간 공유가
> **원리적으로 불가능**합니다. 데모 코드의 보완은 "습관/구조의 시연"이고, 진짜 무결성은
> Supabase 스키마(해시체인·append-only·서버시각·RLS·권한분리)에서만 나옵니다.

## 2. 접수된 9가지 지적 — 대응표

| # | 지적 | 조치 | 남는 한계 |
|---|------|------|-----------|
| 1 | **ON DELETE CASCADE** — 퇴직자 1명 삭제로 결재 이력 전량 소실 | 모든 FK를 `ON DELETE RESTRICT`로 변경. `users.status`(ACTIVE/SUSPENDED/**RETIRED**) 도입 → 삭제 대신 상태 전환. 기안자/결재자 이름·부서·직급은 **시점 스냅샷**으로 별도 컬럼 보존 | 소유자가 SQL로 강제 삭제하면 RESTRICT도 무력 → §5 앵커링으로 "삭제 흔적"을 남김 |
| 2 | **UPSERT 문서** — 승인 후 휴가일수·여비·시간외시간 바꿔치기 가능 | 문서를 **헤더(불변) / 본문 리비전(append-only) / 이벤트(append-only)** 3계층으로 분리. 승인은 "문서"가 아니라 **"그 리비전의 해시"** 에 묶임(`approve_step`이 `content_sha256` 일치를 확인). 데모 코드는 승인 후 `formData` 변경을 차단 | 데모(localStorage)는 진짜 리비전 이력을 못 만듦 — 원리 시연까지만 |
| 3 | **감사 로그 부재** | `approval_events` 테이블 신설 — 상신·승인·반려·회수·전결·폐기를 이벤트로 append. `prev_hash`를 물려 **SHA-256 해시 체인** 구성. `UPDATE/DELETE`를 트리거로 차단. `verify_event_chain()`으로 끊긴 지점 탐지 | 트리거는 소유자가 `DROP` 가능(§5) |
| 4 | **결재 시각을 클라이언트 `new Date()`로 저장** | 모든 시각 컬럼 `TIMESTAMPTZ DEFAULT now()`. 이벤트 시각은 트리거가 `now()`로 **덮어씀**(클라 값 무시). 컬럼 GRANT에서 제외(§9 REVOKE) → 클라이언트가 시각을 못 넣음. 데모 코드는 `nowClientTime()`으로 이름부터 "신뢰 불가"임을 표시 | 데모는 여전히 PC 시계 — 이름으로 경고만 |
| 5 | **날인 이미지 URL 참조 + Public 버킷** | 도장을 `stamp_path`(비공개 버킷) + **`stamp_sha256`(콘텐츠 해시)** 로 관리. 결재 시 해시를 이벤트에 **복사** → 원본을 덮어써도 과거 결재의 도장 해시와 달라 "바뀐 사실"이 드러남. 버킷 Public 해제(가이드에 명시). 데모 코드에 주석 경고 | Storage 실제 비공개화는 Supabase 콘솔 설정 필요(문서로 안내) |
| 6 | **`(docs.length + 1)` 채번** | DB `app.next_document_number()` — 연도별 시퀀스 테이블 + 원자적 `INSERT … ON CONFLICT … RETURNING`. 재사용·중복 없음. 데모 코드는 별도 **단조 증가 카운터**(`DOC_SEQ`)로 교체 — 문서를 지워도 결번이 남음 | 데모 카운터는 동시성 보장 없음(단일 브라우저라 무의미) |
| 7 | **접속기록(조회·출력) 로그 부재 + 민감정보(건강) 자유텍스트** | `access_logs`(VIEW/PRINT/EXPORT/DOWNLOAD, append-only, 서버시각) 신설 + `log_access()` RPC. 병가/모성보호 사유를 **코드값(`leave_reason_codes`) + 증빙 첨부**로 구조화 → 진단명 원문이 본문에 쌓이지 않게 | 앱 UI에서 실제 코드값 셀렉트로 바꾸는 프런트 작업 필요(백로그) |
| 8 | **최고관리자도 못 지우게 — 권한분리·외부앵커링** | authenticated의 **테이블 직접 DML 전면 REVOKE** → `SECURITY DEFINER` 함수(RPC)로만 쓰기. `current_chain_head()` + 매일 외부(이사장·회계사 메일·별도 저장소) 발송 절차 문서화. `service_role` 키가 `VITE_*` 번들에 실리는 사고는 **CI에서 차단**(`.github/workflows/security-guard.yml`) | **단일 프로젝트에서 소유자 조작은 기술로 못 막음**(정직하게 인정) — 목표는 "지우면 흔적이 남는다" |
| 9 | **README에 무결성 등급별 구분표** | README **상단 경고 배너** + [무결성 요구 수준별 바이브코딩 관리 가이드](../README.md#-무결성-요구-수준별-바이브코딩-관리-가이드) 표 추가 | — |

## 3. 추가로 발견한 지점 (지적사항 밖)

접수된 9가지 외에, 감사 관점에서 같이 봐야 할 것들입니다.

### A. 인증·인가가 아예 없음 (가장 근본적인 구멍)
현재 앱은 `sw_edms_current_user_id`를 localStorage에서 바꾸면 **누구나 관장이 됩니다.**
"역할(role)"에 따른 화면 제어는 전부 **화면 장식**일 뿐, 서버가 강제하는 권한이 아닙니다.
→ 운영 전환 시 **Supabase Auth 필수**. 스키마에서 `users.id`를 `auth.users(id)`에 FK로 묶고,
모든 쓰기를 `auth.uid()` 기반 RPC로만 하도록 강제했습니다.

### B. 기존 RLS의 실효성 결함
- 원본 스키마의 `users.id`는 `uuid_generate_v4()` 기본값이라 `auth.uid()`와 **절대 일치하지 않음**
  → `auth.uid() = drafter_id` 정책이 항상 거짓이 될 구조였습니다. (auth 연동으로 수정)
- `CREATE POLICY "Public Users Read" USING (true)` — **익명 포함 전원**에게 이메일·전화·**도장 이미지**까지 공개.
  → `user_directory` 뷰(민감/PII 제외) + 본인 프로필만 조회하는 정책으로 교체.
- `approval_steps`는 RLS만 켜고 정책이 0건 → 결재자 조회가 사실상 막히는 구조였습니다. (정책 추가)
- 문서에 UPDATE/DELETE 정책 부재 → 직접 DML 자체를 REVOKE 했으므로 무력화(RPC 경유만 허용).

### C. 자기결재/결재선 위조 가능성
결재선을 클라이언트가 자유 지정 → 기안자가 자신을 결재자로 넣는 **자기결재**가 가능했습니다.
→ RPC(`submit_document`)에서 서버가 결재자 유효성을 검증하도록 자리를 만들었습니다.
(운영 전 규칙 확정 필요: 자기결재 금지, 직급 역전 금지 등 — 백로그.)

### D. 민감정보의 조회·출력·인쇄 전 구간
병가 사유(건강정보)는 저장뿐 아니라 **조회/인쇄/PDF/엑셀 내보내기** 전 구간이 접속기록 대상입니다.
→ `access_logs` + `log_access()` 신설. 인쇄·내보내기 시 호출하도록 프런트 연동 필요(백로그).
문서 하단 워터마크(열람자·시각) 표기도 권장.

### E. 프런트 비밀키/환경변수 사고
- `.env`가 `.gitignore`에 없었음 → 키를 커밋할 위험. **`.env*` 추가**로 차단.
- Vite는 `VITE_` 접두 변수를 **번들에 그대로 노출**합니다. 프런트에는 **anon 키만** 넣어야 하고,
  `service_role` 키는 절대 금지 → **CI 가드**로 소스/번들 스캔.
- Kakao JavaScript 키는 도메인 화이트리스트를 반드시 설정(미설정 시 키 도용 가능).

### F. 배포 보안 헤더 부재
Vercel/Netlify 배포 시 CSP·`X-Frame-Options`·HSTS 등 보안 헤더 미설정.
→ 배포 가이드에 헤더 예시 추가(백로그: `vercel.json`/`netlify.toml`).

### G. 의존성 취약점
`npm audit` 기준 **high 1건**(`nanoid` <3.3.18, vite 전이 의존성).
→ `npm audit fix`로 해소 가능. CI에 `npm audit` 단계 추가(고위험 발견 시 경고).

### H. 개발 서버 노출
`vite.config.ts`의 `server.host: '0.0.0.0'` — 개발 서버가 LAN 전체에 열립니다.
사내 시연 시 유의(운영과 무관하나 데모 중 민감 시드가 노출될 수 있음).

### I. 입력 검증/XSS 표면
`generateDefaultStampSvg(name)`이 이름을 SVG에 삽입(현재는 data-URI 이미지라 실행 위험은 낮음).
사용자 입력이 `dangerouslySetInnerHTML` 등으로 흘러가지 않도록 유지하고, 서버측 검증을 기본값으로.

## 4. 지금 앱 vs 감사 가능한 전자결재 (격차 요약)

| 항목 | 현재(목업) | 강화 스키마(설계) | 상용/검증 도구 |
|------|-----------|------------------|----------------|
| 기록 저장 | 브라우저 localStorage | Postgres append-only | 문서보존 전용 스토리지 |

## 5. 정직한 한계와 "외부 앵커링" 운영 절차

**단일 Supabase 프로젝트에서 소유자(service_role)는 트리거를 DROP하고, RLS를 우회하며,
SQL Editor로 무엇이든 실행할 수 있습니다.** 위 조치들은 "일반 사용자·앱 경로"의 조작을 막을 뿐,
소유자 조작을 막지 못합니다. 이걸 "막을 수 있다"고 주장하면 지도점검에서 오히려 신뢰를 잃습니다.

그래서 목표를 **"조작을 막는다" → "조작하면 흔적이 남는다"** 로 바꿉니다.

**권장 운영 절차 (기록 생성 주체 ≠ 보관 주체 흉내내기):**
1. 매일 정해진 시각, `select * from app.current_chain_head();` 결과(마지막 seq + head 해시 + 시각)를
   **자동으로 이사장·회계사(외부 계정) 메일 + 별도 저장소**(예: 다른 조직 계정의 스토리지)로 발송.
2. 지도점검·분쟁 시, 그날 DB의 체인을 다시 계산(`verify_event_chain()`)해 **외부에 남은 어제자 head**와 대조.
3. DB를 통째로 되돌리거나 중간을 손대면, 외부 해시와 불일치 → **조작이 드러남.**
4. 발송 주체와 DB 소유자를 **다른 사람**으로 두면 둘수록 신뢰가 커집니다(진짜 핵심은 여기).

> 이것이 외부 업체가 신뢰받는 진짜 이유(기술이 아니라 보관 주체 분리)를 **저비용으로 흉내내는** 방법입니다.

동적 테스트는 실제 소스를 구동합니다 → `npm run test:security` (CI 에서도 실행, 결과 **11/11 통과**).

| 위협 | 방법 | 결과 | 근거 |
|------|------|------|------|
| **SQL 인젝션** | 스키마 정적 분석 | ✅ 표면 없음 | 실행 DB 미탑재(현재 localStorage). 강화 스키마의 쓰기는 전부 **파라미터 바인딩** plpgsql, 동적 문자열 SQL(`EXECUTE '...'`) 0건. `format()` 은 문서번호 문자열 생성에만 쓰이고 실행되지 않음 |
| **SECURITY DEFINER 하이재킹** | 정적 분석 | ✅ 차단 | 모든 `SECURITY DEFINER`/트리거 함수에 `SET search_path` 고정. pgcrypto(`digest`)는 Supabase `extensions` 스키마까지 경로에 포함 |
| **XSS (저장형)** | 날인 SVG 생성기에 `<script>`, `"><img onerror>`, `</text><script>` 등 5종 주입 | ✅ 무력화 | 전체 SVG 가 `encodeURIComponent` → URI 에 리터럴 `<script>` 없음. 입력은 3자로 절단되고 `<img src>` 로만 렌더(SVG-as-img 는 스크립트 미실행) |
| **XSS (DOM 싱크)** | `dangerouslySetInnerHTML`/`innerHTML`/`eval`/`document.write`/`<iframe>`/`background:url()` 전수 grep | ✅ 없음 | React 기본 이스케이프. 위험 싱크 0건 |
| **문서번호 변조/재사용** | 문서 삭제 후 재발급 | ✅ 방어 | 단조 증가 카운터 — 삭제해도 번호가 되돌아가지 않음(결번이 증거로 남음) |
| **승인 후 본문 바꿔치기** | APPROVED 문서 `formData` 수정 시도 | ✅ 차단 | `updateDocument` 가 예외 발생(불변 가드) |
| **프로토타입 오염** | 조작된 localStorage 의 `__proto__` 페이로드 | ✅ 안전 | `Object.prototype` 미오염 |
| **시크릿 유출** | 소스·`dist` 번들 스캔(service_role/JWT/PEM/키) | ✅ 없음 | CI `security-guard` 가 지속 차단 |
| **의존성 취약점** | `npm audit --omit=dev` | ✅ 0건 | (nanoid 취약점은 dev 전용 vite 전이 의존성 → 배포 번들 미포함) |
| **클라이언트 신원 위조** | `current_user_id` 조작 | ⚠️ **재현됨(의도)** | 목업엔 서버 인가가 없어 누구나 "관장" 위장 가능 → **A등급 운영 시 Supabase Auth+RLS 필수**(본 문서 §3-A) |

> 요지: **현재 코드에 SQL 인젝션·XSS·시크릿 유출 표면은 없습니다.** 남는 **가장 큰 실질 위험은
> "인증·인가 부재"**(localStorage 목업의 본질적 한계)이며, 운영 전환 시 Supabase Auth + RLS + RPC 로만 닫힙니다.
> 재현 방법·커버리지는 [docs/security/README.md](security/README.md) 참고.
